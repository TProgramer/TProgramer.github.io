# 개인정보를 DB에 저장할 때 고려할 점

지금 제가 진행하고 있는 투닝 강사님의 강사료 정산, 원천징수 영수증 발급, 프리랜서 사업소득 신고 등 세무/회계 처리를 위해 주민등록번호와 같이 유출에 민감한 개인정보를 불가피하게 DB에 수집·보관해야 하는 일이 생겨 이를 해결한 과정을 소개합니다.

우선 주민등록번호는 대한민국 개인정보보호법에 따라 엄격한 기술적·관리적 보호조치가 요구되는 민감정보입니다. `개인정보보호법 제24조의2 및 제29조 (안전조치의무) 주민등록번호는 법적 근거 없이 수집할 수 없으며, 분실·도난·유출·위조·변조 또는 훼손되지 아니하도록 암호화 등의 안전성 확보에 필요한 조치를 반드시 취해야한다` 고 합니다.

하지만 단순히 `AES-256` 암호화 방식으로 생성된 대칭키를 서버의 환경변수로 두고 암호화하는 방식은 서버가 공격당하거나 대칭키가 노출되는 즉시 모든 개인정보가 복호화되는 큰 위험이 있어 윤리적/법적 문제가 크다고 보았습니다. 이러한 문제를 해결하기 위해 AWS KMS 기반의 봉투 암호화 체계를 설계해보았습니다.

## 봉투 암호화란?

봉투 암호화는 데이터를 암호화하는 키(Data Encrypt Key)와 그 키를 다시 암호화하는 마스터 키 의 2계층 키 관리 구조를 사용하는 암호화 방식입니다. 편지를 봉투에 넣고(데이터 암호화), 그 봉투를 다시 튼튼한 금고에 넣거나 인장으로 봉인하는(키를 마스터키로 암호화) 비유에서 유래되었습니다.

# AWS KMS를 활용한 이유

여기서 암호화에 사용할 키를 안전하게 생성, 보관, 관리의  위해서 주로 HSM(Hardware Security Module)이라는 장비를 사용하는데, 이를 AWS KMS에서 저렴한 가격으로 서비스해주기에 활용하였습니다. 또한 누군가 

> KMS에 대한 자세한 소개는 [공식문서](https://docs.aws.amazon.com/kms/latest/developerguide/overview.html) 참고 바랍니다.

위 주민등록번호를 DB에 저장하는 과정을 예로 들면

1. 서버가 AWS KMS에 `GenerateDataKey` 요청을 보냄
2. KMS는 메모리에서 사용할 `평문 DEK` 와 KMS 마스터 키로 암호화된 `암호화된 DEK` 두 가지를 반환
3. 서버의 메모리 안에서 `평문 DEK`와 `iv(initialization vector, 즉 salting 용 난수)`를 이용해 주민등록번호를 대칭키 알고리즘(AES-256-GCM)으로 암호화
4. 암호화가 끝나면 메모리에 머물던 `평문 DEK`는 따로 저장하지않은채로 휘발시킴
5. `암호화된 주민번호`와 KMS로 암호화된 `암호화된 DEK`, `iv` 값 을 DB 레코드에 저장

암호화한 데이터를 관리자가 조회한다고 하면

1. DB에서 조회 대상의 `암호화된 주민번호`와 `암호화된 DEK`, `iv` 값 을 가져옴
2. `암호화된 DEK`의 복호화를 AWS KMS의 `Decrypt` API로 요청
3. KMS는 내부 하드웨어 보안 모듈(HSM)에서 관리하는 마스터키로 `암호화된 DEK`를 풀어 **`평문 DEK`** 를 반환
4. 서버는 전달받은 `평문 DEK`로 암호화된 주민번호를 복호화 (`평문 DEK`는 위와 동일하게 휘발시킴)

의 순서로 암호화된 데이터의 평문을 확인하게 됩니다.

# 직접 구현하기 vs AWS KMS 를 사용해 구현하기

* 직접 구현하는 비용과 미래의 유지보수 비용 대비  예상비용이 매우 적어서,
    직접 구현보다 구현이 쉬운 AWS KMS 를 활용하고자 함
* 강사님들/관리자 전용 서비스여서, 하루에 예상되는 요청 수도 적고, 기존 On-call 방식도 병행하기에 장애 상황에도 크게 민감하지 않음
